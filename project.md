# Agentic Coding Workflow

I find myself from time to time wanting to re-establish my agentic coding practices and usually when I do this it is because I have run into a certain number of walls in my current execution. The two killers in agentic coding tend to be token waste and poor planning. They typically go hand in hand. You spend hours coming up with the perfect spec that captures everything, you then ensure the plan has everything you need, and then you let it implement for a few hours and it comes back with a broken product. Nothing is more frustrating than this. The key thing here is its not the agents fault, but my own fault in not leveraging the agent properly. I was not actually sure on the end shape I wanted. I was not specific on what needs to make up the end result, not just want i want product shape to be. I've spent time working on improving a product in a simulation type shape and when I say okay now make this behavior part of the physical app harness, I don't think I've ever once recieved a working product.

This usually makes me rethink how I develop and I try to establish new practices to carry forward. The hardest part of agentic coding is maximizing the way you can utilize an LLM with the most recent tools that came out. It has come a long way from where it started. There are tools like langgraph and pydantic AI which I have not looked at too closely yet, but seem like great ways to make your own AI assistants. Developers are constantly publishing their own work and workflows that its up to me to pause development, read into it, implement their solutions, and then continue my own development. This is really difficult when you are trying to ship a product yesterday. However, in this world the few steps backwards will likely move you forward a lot faster.

I want to focus in on how I've approached my workflow from my first day vibe coding to now. 

## The Early Days

This was the wild west of vibe coding. You take an out of sorts mechanical engineer with a free subscription to codex (I already had a paid subscription to ChatGPT for other purposes) and let the reigns loose. My workflow was probably as bad as it could get, but I quickly learned a few important things. 
1. AI was better at prompting than I was
2. A reviewer/testing was necessary to look at the current code produced and determine if it would actually do as intended
3. A working perpetual memory was needed so you can easily onboard new agents when the context was too full

I used the general chat bot to be my copilot in agentic coding since it knew how to use the system much better than me. I realized it quickly got a bloated context window and would struggle to work. I had it write me prompts, review the work of the AI agent, and help me drive to the next steps of the project.

The things I did poorly.
1. I was using the web version of codex. Which meant I was also using github as the main source of git management.
2. I did not prune any branches
3. I would merge code before another agent of mine would validate it
4. I had validation loops that went no where and I had no understanding of why

All these things were symptoms of me having no clue what I was doing. I was as people put it "just vibing." However, my vibing was actually building some very foundational habits that are an extension of my workflow in anything. It pushed me to try something new and not accept not understanding it as a barrier of entry. This was just my first step in development.

## Using Multiple Platforms

As anyone that starts to get their hands dirty with agentic coding, you quickly start to run out of credits. I was just using it for fun, but I saw the real value in what can be built. I was working on my main app, which I look at now and it is a very simple piece of technology, but it has taught me a lot about the building process. I also had scattered little side projects going on at the same time and that was where I saw the potential of what can be built using AI agents. I am aware that AI agents powered by me cannot make code better than a staff developer, but my AI agents can make code significantly better than myself. 

I decided it was worth investing my time and resources into using it because of what can be developed with agentic coding. I subscribed to the ~$20 plan that both OpenAI and Anthropic provide and started using multiple platforms. This allowed me to switch between platforms as I ran out of credits, but it pointed to some incredibly important items. I needed to be able to have a stopping point that a completely fresh agent can pick up. I needed to learn some of the casual differences between the two different platforms (to be honest, I am still learning them to this date). I developed my own system to doing this. I realized it was really hard for me to pick up exactly where I left off so I started to do twin development. Work on building two apps at the same time instead of ensuring my project was always ready to be picked up by a new agent when I ran out of tokens in my window.

A friend of mine shared a McKinsey article about waterfall workflows and a created my own local version of this that worked great. It significantly improved the outcomes of what I was building, but as it seems to be a constant theme, increased my token usage. I discovered Claude /plan and really liked that feature to get me out of using the chat bot for brainstorming and planning. I even had my claude bot build me an equivalent to have my codex agent use before ChatGPT made an equivalent. My workflow started growing and improving, but I wil admit my practices were still very disorganized. 

I still remain in the same boat I was in a long time ago, switching between platforms is not simple, but requires significant amount of forethought. Even now, with the current workflow I have been building I am still thinking about the setup needed to maximize codex and claude at the same time. For others they may also be looking at other platforms they use and ensuring it works for that too. I don't envision myself using different platforms for the same project just because it requires too much context switching for myself, but I want robust workflows that are platform agnostic and allow me to switch back and forth as I desire. 

## Optimizing Agentic Coding Workflows

After doing this exact thing for months, this is my conclusion. You will never be optimized. The second you find a good place, it will quickly become outdated. You learn how to prompt perfectly and a new model essentially removes the need for everything you learned. You started developing skills for ai agents and now the agents pre-load those exact skills but better. Everything you customize tends to be the same thing everyone else is customizing and chances are someone smarter than you has already come up with a better solution.

So what can we do? We adapt. The interesting thing with development in any sense of the word, is no one has the exact same workflow. Chances are if you adopt someone elses workflow you will find things you like and dislike about it. Ways you can further improve how to execute. You can download 100s of skills, but if your prompts only activate 5, than the other 95 are useless. My latest exercise in optimizing my workflow taught me I've got a lot to improve. I made a generic workflow based on my favorite parts of /superpowers, but quickly realized a lot of the items I built were either to shallow or excessive. It was a lot more back and forth for approvals that were unnecessary. I still have the same shortcomings as before. There was a lot that needed to be improved from what my starting point was.

## My Current Workflow

I took this blank workflow and decided I wanted to test two things. Whether my handshake knowledge can be easily applied to a simple application and if my workflow template actually works as intended. Out of the gate, it had a lot of issues. One it was extremely unclear on how I should even be using it. There were a lot of files disorganized that my prior AI agent made to help explain things. I at least determined how to use it, but the specs and plans it wrote me were extremely shallow. I also came up with a list of prompts to give for various reasons, but it was very annoying having to find that prompt in the list before I wanted the agent to complete something. There were many other items I liked or disliked, but the good thing was I was improving the system as I went and built out the application. The good news, the actual application was built very fast. Maybe in a matter of 1 day from end to end. It has actually been all the clean up steps and improvement to the workflow as well as non specified parts of the product that I turned into the product that caused some delay in execution. 

Okay, now I will get to the actual workflow.
1. Spend some time talking to a web chatbot about your project idea
2. Import an extremely detailed project overview file into the seed repo with the workflow pre-loaded
3. Submit seed prompt to begin creating foundational documents from the project overview file
4. Write first spec and plan, approve, then begin implementation
5. Repeat spec and plan writing until you get the product described in project overview
6. Realize you want more than what was described in the project overview file and build without clear direction
7. Realize this is bad and you need to re-evaluate development
8. Build what you wanted, but in a longer flow with more headache than necessary

Now, for this little project I was building, none of this really mattered. My workflow was built for larger projects so this project only needed one spec and plan and I had the entire app for the most part. It did teach me some important things that I realized happen in every project I engaged in. I have this idea of what I want built, I start building it, I realize it needs something else, or that I didn't fully design in how it will be built, I rush through the remediation plan. Sometimes its fine, other times I'm in the most frustrating loop I could imagine. I write a well crafted spec, I write a great plan, and then it still doesn't build what I need. This gets back to one of the most important things, we need to use these lessons in our own development to customize how we design our workflow. Perhaps a more seasoned developer defines things better from the beginning of a project and his ai agent doesn't make the same mistakes. This developer won't need as strong of guardrails as perhaps I do. I have learned a lot about both software development and agentic coding that continually influence what I build and how I build it.

## Concluding Thoughts

There are many workflows someone can choose and the one I decide on may not match exactly what best serves you. What I can say is the best way to find what works for you is by trial and error. You can only know so much about deployment from reading about it, its not until you realize you need a server to run a backend, a website or application to run a frontend, and APIs all over the place to connect everything that you realize defining these things ahead of time would likely ensure the code you built integrates into the way you want to deploy it. Then you start making sure this is built into the beginning scaffold. Its not until you realize that a static webpage is very cheap to deploy over a webpage that requires a running backend that you may design a frontend only application over one with a backend. its not until you realize that this application if it has secrets you don't want easily accessible to the internet will still need some protective layer if you do not have a functioning backend. With everything you learn you adjust the way you execute. If you take a look at my current workflow template you will see the most up-to-date version of it. I try to carry what I learn from project to project and incorporate it into my workflow. The workflow of today can only be developed by the shortcoming of yesterday's workflow. 

Although I've specified this strictly for the world of agentic coding, the workflow updates is also how I handle every other aspect of personal and work development. I'm learning a language, well what helped me learn. How can I improve my workflow. I'm running 5 projects simulateneously, I'm not propelling any one of them forward. Maybe I need more planning in my execution strategy. Every part of my life needs to be constantly improved so that I minimize stagnation. The biggest change I've widely incorporated has been planning. I need to sit down and think about what it is I'm doing. I love being gung-ho and going straight to the project, but that only works well if there is a well-written plan to get to the goals. That is not to say we should stay in plan mode forever, but a good plan makes execution far easier than a straight to product approach. I'll be sharing this approach in action with one of my upcoming robotics projects.
